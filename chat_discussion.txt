## [2026-09-08] Render Dynamic Port Binding
- Render dynamically assigns a port via the `$PORT` environment variable.
- The C++ server was hardcoded to bind to `8080`, causing Render's health checks to fail and the server to exit after 6 seconds.
- Fixed the issue by using `<cstdlib>` and `std::getenv("PORT")` in `main.cpp` to dynamically bind to the cloud provider's assigned port, ensuring successful PaaS deployment.

--- 2026-09-09 CORS OPTIONS 502 Root Cause Analysis ---
Root cause 1: Frontend 'Backend offline' error was caused by API_BASE = '/api' (relative path) pointing to the SAME host as the frontend static site, not to kvault-db.onrender.com. Fixed by creating dashboard/.env.production with VITE_API_URL=https://kvault-db.onrender.com/api.
Root cause 2: Crow's router at routing.h:1638 hardcodes es = response(204) for ALL OPTIONS requests before after_handle runs. The fix: FixEmptyResponseMiddleware.after_handle() intercepts and changes res.code=200 and res.body='OK'. Locally confirmed: OPTIONS returns 200 OK on wire despite Crow log showing 204. The  fter_handle approach works because prepare_buffers() reads from es.code AFTER after_handle runs.
Key finding: 
es.completed_ is private in Crow. The  efore_handle res.end() approach appeared to work but the Crow log and debug prints confirmed it was actually  fter_handle doing the work. The  efore_handle res.end() does NOT prevent the router from running because complete_request_handler_ is nullptr when before_handle runs.

### 2026-09-12: Fixing Crow OPTIONS Proxy Truncation Bug ###
- Deep debugging revealed that while the `after_handle` middleware approach correctly changed the 204 to 200 OK locally, it triggered a massive bug in Crow (v1.2.0) that caused production proxy deployments (Render, Vercel) to drop the connection.
- Because Crow natively intercepts `OPTIONS` requests and sets `res.end()` *before* our middleware ran, `complete_request()` was ultimately invoked **twice** for the same connection.
- The second invocation of `complete_request()` executed `prepare_buffers()`, which `clear()`ed the ASIO `async_write` buffers mid-flight.
- This race condition systematically truncated the `WSASend` operation exactly after the `Content-Type: text/plain` header, stripping the crucial `\r\n` terminator and `Content-Length: 2` header, leading to `ERR_EMPTY_RESPONSE` from proxies expecting valid HTTP frames.
- Resolved this permanently by injecting a Python patching script (`patch_crow.py`) into the CMake `FetchContent` pipeline. It overrides `req.method == HTTPMethod::Options` to `false && ...` in `crow/routing.h`, bypassing Crow's flawed native preflight router.
- Our custom `FixEmptyResponseMiddleware` now exclusively processes the unhandled 404 into a valid 200 OK CORS response safely, without buffer corruption.

### 2026-09-12: Zero-Dependency Build Architecture & Render Cold Starts ###
- **Build Infrastructure Resilience:** The initial Python-based patch script failed on Render because minimal Docker base images (e.g., Alpine or `ubuntu` without `python3`) threw fatal CMake errors when `find_package(Python3 REQUIRED)` couldn't resolve the interpreter.
- Instead of polluting the `Dockerfile` with external script dependencies that are prone to cache-bust failures and environment disparities, we completely removed `patch_crow.py`.
- **Native CMake File Manipulation:** We leveraged CMake's built-in file APIs (`file(READ)` and `string(REPLACE)`) to patch `routing.h` natively during the build phase. This guarantees a 100% portable, zero-dependency source modification that works universally across Linux, Windows, and container environments without relying on external tooling.
- **Render Cold Start UX Considerations:** Render's free tier spins down web services after 15 minutes of inactivity. When a Vercel frontend `fetch()` triggers a "cold start", the container takes 30-120 seconds to boot. During this time, Render holds the TCP connection open, but frontend clients or browsers often hit internal 10-30s timeouts, throwing false "Connection Refused" errors before the backend completes initialization. We noted that a standard mitigation is keeping the server perpetually awake via a cron job ping, or gracefully handling prolonged initialization delays in the React UI.
